# e2e-стенд splitr на Docker

Полностью автоматический сквозной прогон продукта: демон, менеджер туннеля,
сторож pf, HTTP API и CLI проверяются на живом sshuttle между двумя реальными
сетями.

```bash
make -C test/docker docker-test
```

Один вход, никакого sudo на хосте, ключи ssh генерируются на лету во временный
каталог вне репозитория, стенд гарантированно убирается за собой (`trap` в
`run.sh`), код возврата — результат `go test`.

## Как устроен стенд

```
        net_front 10.77.1.0/24              net_back 10.77.2.0/24
   ┌──────────────┐        ┌───────────────────────┐        ┌──────────────┐
   │   client     │──ssh──▶│        remote         │───────▶│    target    │
   │ 10.77.1.10   │        │ 10.77.1.20/10.77.2.20 │        │  10.77.2.10  │
   │ splitr+    │        │  sshd + python3       │        │    nginx     │
   │ sshuttle     │        └───────────────────────┘        └──────────────┘
   └──────────────┘
          ╳ прямого пути в net_back нет (docker разводит бриджи)
```

* **target** — nginx, отдаёт опознавательную строку `SPLITR-E2E-TARGET-OK`,
  висит только в `net_back`.
* **remote** — alpine с sshd (вход по одноразовому ключу) и python3: серверная
  часть sshuttle написана на питоне. Стоит в обеих сетях.
* **client** — образ, собранный из этого репозитория (`golang:1.26-bookworm` +
  sshuttle + iptables), `cap_add: NET_ADMIN`. Внутри него запускается демон
  `splitr daemon` и гоняются тесты `test/e2e` с тегом `docker_e2e`.

Доступность target — честный индикатор туннеля: без sshuttle пакеты из client в
`net_back` не проходят вообще (docker разводит бриджи разных сетей правилами
`DOCKER-ISOLATION-*`), а при живом туннеле sshuttle перехватывает их через
iptables и уносит на remote.

## Чего стенд принципиально НЕ проверяет

**Решения ядра pf о пакетах.** `pf` есть только в macOS/BSD; в Linux-контейнере
его нет и быть не может. Поэтому `/sbin/pfctl` в клиентском образе подменён
стабом (`client/pfctl-stub.sh`), а проверяется всё, что вокруг:

* корректность генерируемых правил (текст якоря, таблицы, `quick` в panic-режиме);
* последовательность и содержание вызовов `pfctl`, которые делает демон
  (журнал `/var/lib/pfstub/calls.log`);
* реакция демона на состояние pf: пропавший якорь, неподключённый якорь,
  выключенный pf, появление и исчезновение якоря `sshuttle-<port>`.

Что остаётся непроверяемым здесь и требует ручной проверки на macOS:

* что `block drop out on ! lo0 ... to <splitr_block>` действительно роняет
  пакеты, а `pass out route-to lo0` от sshuttle его перебивает (last-match-wins);
* поведение `pfctl -E`/`-X` со счётчиком ссылок настоящего ядра;
* `pfctl -k` (сброс живых состояний) — стаб только логирует вызов;
* подключение якоря из `/etc/pf.conf` при загрузке системы, launchd, `install`/
  `uninstall` (правки системных файлов macOS).

Также в контейнере sshuttle работает методом `nat`/iptables, а не через pf, как
на macOS: проверяется сборка командной строки, жизненный цикл процесса и факт
переноса трафика, но не macOS-специфичный способ перехвата.

## Стаб pfctl

`client/pfctl-stub.sh` кладётся в образ по пути `/sbin/pfctl` — именно его зовёт
`pfctl.New()`. Состояние: `/var/lib/pfstub` (`main.rules`, `anchors/*.rules`,
`enabled`, `tokens`), журнал вызовов: `/var/lib/pfstub/calls.log`.

Эмулируется: `-E` (печатает `Token : N` в stderr), `-X <token>`, `-s info`,
`-s rules`, `-s Anchors`, `-a <anchor> -f -`, `-a <anchor> -F all`,
`-a <anchor> -s rules`, `-F all` (чужой сброс всего), `-f <file>` (перечитать
`/etc/pf.conf` вместе с `load anchor ... from ...`), `-k`.

Ключевой момент: `-s Anchors` печатает `sshuttle-12300` ровно тогда, когда в
системе действительно жив процесс sshuttle (`pgrep -f sshuttle`). Именно по
этому признаку демон считает туннель поднятым, поэтому в стенде сигнал
привязан к реальному процессу, а не к флажку в файле.

## Что покрыто тестами

| Тест | Что проверяет |
|---|---|
| `Test001BaseIsolation` | без туннеля net_back недостижима, remote — достижим |
| `Test002TunnelUpDown` | `up` поднимает sshuttle с правильной командной строкой, target отвечает через туннель; `down` гасит процесс и доступ пропадает; поля `tunnel/profile/pid/blocking/sshuttle_anchors` до/во время/после |
| `Test003WatchdogRestoresAnchor` | чужой `pfctl -F all` при опущенном туннеле чинится сторожем: правила якоря загружаются заново и `pf.conf` перечитывается |
| `Test004WatchdogKeepsTunnel` | при живом туннеле сторож НЕ трогает `pf.conf` (это порвало бы туннель), а только жалуется в `warnings`; туннель выживает; после `down` подключение якоря чинится |
| `Test005TunnelKilled` | внешний `kill -9` замечен, состояние уходит в down/failed, блокировка на месте |
| `Test006Autoreconnect` | с `autoreconnect: true` туннель поднимается заново сам и снова работает |
| `Test007HTTPAPI` | `/status /config /rules /up /down /protect /reload /probe /`, коды 200/404/405/500 — и через unix-сокет, и через TCP |
| `Test008CLI` | `status`, `status --json`, `up`, `down`, `protect strict/on`, `rules`, `probe`, `validate`, неизвестная команда |
| `Test009ReloadChangesRules` | правка конфига на диске + `reload` меняет набор блокируемых сетей (в `/rules`, в статусе, в якоре и в файле якоря); битый конфиг отвергается |
| `Test010Idempotency` | повторный `down` при опущенном туннеле — не ошибка; поведение повторного `up` при живом туннеле |

## Что стенд уже нашёл в продукте

* **Повторный `up` при живом туннеле убивает туннель.** `Daemon.Up` зовёт
  `runner.KillForeign()`, а тот считает чужим любой процесс из
  `pgrep -f sshuttle`, кроме собственного прямого потомка. sshuttle всегда
  держит вторым процессом `sshuttle --method auto --firewall` — его и гасят.
  Клиент получает 500 «туннель уже поднят», а туннеля к этому моменту уже нет.
  Зафиксировано в `Test010Idempotency` / `assertRepeatedUp` (падает в безопасную
  сторону: защита снова режет трафик).
* **`KillForeign` слишком широк**: под `pgrep -f sshuttle` попадает любой
  процесс, у которого строка `sshuttle` встречается в командной строке
  (редактор с открытым конфигом, `grep`, скрипт-обёртка).
* **`blocking` восстанавливается не мгновенно**, если якорь оказался
  неподключённым: подключение чинится только следующим тиком сторожа и только
  при опущенном туннеле. В стенде это видно как «tunnel=failed, blocking=false»
  на один-два тика после падения туннеля.

## Отладка

```bash
make -C test/docker docker-test-up     # прогнать и оставить стенд поднятым
make -C test/docker docker-test-shell  # bash внутри client
make -C test/docker docker-test-down   # убрать
```

Полезное внутри client:

* `/var/log/splitr.log` — лог демона;
* `/var/lib/pfstub/calls.log` — все вызовы pfctl;
* `/sbin/pfctl -a splitr -s rules` — что «загружено» в якорь;
* `splitr status` — CLI ходит в тот же сокет `/var/run/splitr.sock`.

Переменная `SPLITR_E2E_KEEP=1` оставляет стенд после прогона.
